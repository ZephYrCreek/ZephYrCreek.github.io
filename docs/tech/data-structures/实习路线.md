如果你开学后绝对无法每周实习3—4天，那么寒假Offer本身就应当视为低概率目标，主战场应放在2027年暑期。

## 二、岗位投递分层

|层级|目标岗位|定位|
|---|---|---|
|冲刺|字节、美图、阿里等Agent/AI应用开发|检验上限，不作为保底|

|扩展|Python后端、内部AI工具、AI平台/评测开发|增加岗位宽度|
|替代|校内实验室工程项目、导师课题组开发任务|寒假实习不成功时积累项目|

检索岗位时使用这些名称：

- AI应用开发实习生
- 大模型应用开发实习生
- LLM/RAG开发实习生
- AI后端开发实习生
- Agent研发/开发实习生
- Python后端实习生（AI方向）
- 大模型平台/评测开发实习生

看到以下要求时需要谨慎区分：

- 主要要求FastAPI、RAG、数据库、Tool Calling：可以投；

- 要求CUDA、TensorRT、分布式训练、C++：属于Infra，不投；
- 只写Prompt、搭工作流、整理数据：可以作为保底，但成长性需要判断。

## 三、9月至11月的准备路线

### 第一阶段：9月——成为能独立写项目的Python开发者

不要重新完整学习一遍Python课程，直接扩展`jd_extractor`，遇到缺口再补。

需要掌握：

- Python模块、函数、类、类型注解；
- 异常处理和调试；
- FastAPI、HTTP、REST API；
- Pydantic；
- SQL基础；
- SQLite起步，随后迁移PostgreSQL；
- Git基本工作流；
- pytest测试；
- 日志和配置文件；
- Docker基本部署。

项目阶段成果：

```
POST /jobs/extract
GET  /jobs
GET  /jobs/{id}
POST /evaluations
```

系统能够：

1. 接收一段JD；
2. 调用模型完成结构化抽取；
3. 用Pydantic验证；
4. 存入数据库；
5. 返回证据片段；
6. 对失败请求记录日志；
7. 通过测试验证核心函数。

9月底验收标准：

- 能独立增加一个API接口；
- 能解释请求进入系统后的完整流程；
- 能根据报错定位模块、路径、类型或数据库问题；
- 项目不是只有一个`main.py`；
- 有测试、README和可复现的运行方式。

如果9月底这些还没完成，暂时不要进入LangGraph和复杂RAG。

---

### 第二阶段：10月——增加RAG和评测

这一阶段的重点不是“接入向量数据库”，而是证明系统效果。

#### 1. 建立小型评测集

手工整理50—100份允许使用或匿名化的JD，标注：

- 公司；
- 岗位；
- 学历；
- 实习时长；
- 技能要求；
- 对应原文证据。

比较：

- 规则抽取；
- 单次LLM抽取；
- 改进后的分阶段抽取。

指标可以包括：

- 字段准确率；
- 技能字段Precision、Recall、F1；
- 缺失字段识别率；
- 无证据结论比例；
- 单次调用成本和延迟。

#### 2. 实现招聘信息检索

依次实现：

1. BM25关键词检索；
2. Embedding向量检索；
3. 混合检索；
4. 可选Reranker。

使用Recall@k比较不同方法，而不是只展示“可以搜索”。

#### 3. 加入可靠性设计

- 结构化输出失败后的重试；
- 超时处理；
- 重复JD去重；
- 模型返回结果缓存；
- 每条结论附原文证据；
- 低置信度结果交给用户确认。

10月底的成果应当是一份可展示的实验结论，例如：

> 在80份JD上，混合检索的Recall@5由某基线提升到某结果；证据约束使无依据字段比例下降。

数字必须来自真实运行。

### 第三阶段：11月——部署、Agent和求职

只有当前两阶段完成后，才加入一个Agent工作流：

```
读取简历
→ 检索目标岗位
→ 提取岗位要求
→ 对比已有技能
→ 调用工具生成学习差距
→ 用户确认
→ 输出带证据的分析报告
```

先用普通Python函数实现，再决定是否使用LangGraph。

Agent部分只需要掌握：

- Tool Schema；
- Function Calling；
- 状态传递；
- 超时和重试；
- 人工确认；
- 简单Memory；
- Trace、成本和延迟；
- 一个MCP工具的使用与原理。

不做：

- 多Agent辩论；
- 自主无限循环；
- Agentic RL；
- 同时学习多个Agent框架；
- 没有实际必要的复杂Memory。

11月项目需要完成：

- Docker部署；
- 在线演示或演示视频；
- 清晰README；
- 系统架构说明；
- 评测结果；
- 典型Bad Case；
- 为什么采用这些技术的解释。

## 六、投递与止损机制

从10月底开始投递，不等项目“完全完成”。

建议每周：

- 精选10—15个符合毕业年份和时间要求的岗位；
- 优先北京、远程或能够延续到开学后的岗位；
- 针对JD修改项目描述；
- 记录投递、回复、面试和失败原因。

设置三个判断节点：

### 11月中旬

如果项目仍没有评测结果：

> 停止增加Agent功能，优先完成部署、评测和README。

### 累计投递约30个有效岗位后

- 完全没有面试：检查毕业年份、实习时长、简历和项目表达；
- 有面试但算法挂：增加算法训练；
- 项目追问挂：减少功能，深入理解现有系统；
- 后端问题挂：补HTTP、数据库和Python；
- RAG问题挂：回到评测和Bad Case分析。

### 12月以后

如果大量岗位都要求4—6个月，而你只能寒假实习：

> 不应把失败解释为技术路线错误，应把目标转向2027年春季/暑期，并尝试校内科研或实验室工程项目。
